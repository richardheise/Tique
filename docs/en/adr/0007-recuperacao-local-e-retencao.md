# Automatic local recovery and retention of inactive vaults

User-approved decision on 25/10/2026. Normal use should not require managing Android files. This implementation covers only the synthetic proof; it does not enable real data.

The default is to keep up to three private encrypted copies, without raw payloads, created by the Kotlin executor when the core runs. There is at most one copy per 24-hour interval and only when records/parsing have changed. The first non-empty copy may be created immediately. A clock moving backward delays the next copy; it does not waive the interval. There is no permanent schedule, additional service, or JavaScript dependency. After force-stop, work waits until the core runs again.

Copies use their own random AES-256 key wrapped by Android Keystore. Each file uses AES-GCM with a random nonce and AAD that distinguishes the copy index and identity; both index and content are encrypted and authenticated. A copy is read/verified before the index is published via AtomicFile. Orphans are removed only after authenticating the index. Key loss, an invalid index, or a modified copy blocks recovery without replacing files or changing the active vault. Restoration reuses the staging and vault-switch flow defined in ADR 0006 without merging records.

Private copies depend on the installation and Keystore. They do not protect against uninstall, device loss, or every key-loss scenario; they are not portable backup. The screen explains this. “Advanced settings” groups activation, listing/restoration, explicit disposal, and password-protected portable backup. Disabling preserves existing copies. Deleting copies disables recovery first and does not delete observations in the active vault. Portable backup remains optional and requires explicitly choosing a local destination outside the app; without it, survival after uninstall is not promised.

Alternatives considered: requiring manual files each time adds friction; automatic export to a public folder would require managing authorization/destination and would not remove the need for a portable password; embedding a portable key would prevent effective protection; keeping only the previous vault provides no recovery history. The cost is up to three snapshots limited to 8 MiB each, auxiliary index/key storage, and a recovery policy separate from portable backup. The policy will also apply to the financial ledger once it exists in protected mode; the current proof does not copy the Expo Go database.

Raw payloads expire 30 days after capture time in both active and previous vaults, without activating the previous one. Comparisons use Instant to respect different ISO timestamp fractions. Cleanup preserves observations, identities, parsing, and metadata; pending items without raw data are explicitly unavailable for reprocessing. The database uses secure_delete, in-memory temporaries, and, when there is a WAL, a verified TRUNCATE checkpoint. This does not promise physical erasure of older pages from flash storage or work while the app is not running.

If the previous vault cannot be opened with its key, show “cleanup blocked,” pause capture, and preserve files. Resolution requires restoring access or explicitly discarding the previous vault in advanced settings. Automatically deleting the vault, retaining raw data indefinitely without notice, or reopening a missing database as empty were rejected. Cleanup is attempted when opening/querying the core and after durable capture; the background path uses the next expiry to avoid reopening the previous vault for every event.

The executable interface suite uses isolated synthetic vaults, preferences, and aliases. The same 28 scenarios make up the instrumented tests; compilation is not execution. There is also interrupted-sandbox cleanup and bounded reading of the process's own logs, with positive controls. Inaccessible logs or missing controls produce “not verified.” Even an approved result covers only the observed window and tested probes; it does not certify universal absence of logs. Neither READ_LOGS permission nor broad file access is needed.

Sources and verified APIs: [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile), [Keystore](https://developer.android.com/privacy-and-security/keystore), [SQLCipher Android v4.19.1](https://github.com/sqlcipher/sqlcipher-android/tree/v4.19.1), [SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/), and [logcat](https://developer.android.com/tools/logcat). Differences between PRAGMAs that return rows and setters without a return value were checked in the installed driver; they are not interchangeable.
